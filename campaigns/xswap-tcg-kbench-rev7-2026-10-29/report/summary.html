Where c1c sits: system → subsystem → change

Schematic, not measured. Wording from the candidate record and the review.

Linux memory management→swap-in path (page fault on a swapped-out page)→mm/swap_state.c readahead for xswap slots
  • System. When a process touches memory that was swapped out, the kernel reads it back (“swap-in”). Readahead also reads neighbouring slots, betting they will be needed next.
  • Subsystem. xswap is the project's swap layer; baseline 5e84ca92 skips readahead for xswap slots.
  • c1 (round 1). Turned readahead on for xswap faults on every backend. Disk got faster, but zram (a synchronous, in-memory backend) got a heavier tail.
  • c1c (round 2). Same idea, plus a safety gate: readahead only when the physical backend is asynchronous and writable, with a recheck under the cluster lock after the page enters the swap cache that drops the speculative page before any read (campaigns/xswap-tcg-kbench-rev7-2026-10-29/candidates/v2-c1c-xs-ra-safe.json hypothesis). One file changed (mm/swap_state.c), 199 changed lines, SCOPE_PASS; commit b69e47c9, parent = baseline 5e84ca92.
  • Expected trade. Disk sequential swap-in faster; zram back on the baseline path (readahead ≈ 0, tail ≈ unchanged). Pre-registered KILL: median zram seq.p99 ratio below 0.834.
